# 首轮本机调度实验 · 2026-11-05

Windows amd64、Go 1.27.3；仅采集调度时间戳，不发送任何真实输入。

| 1ms 目标间隔 | P50 | P99 | 最大间隔 | 单核 CPU 占用 |
|---|---:|---:|---:|---:|
| 现有 C++ 调度器 | 1.0000ms | 1.0003ms | 1.0315ms | 99.98% |
| Go 高分辨率等待 | 1.0260ms | 1.5125ms | 2.4134ms | 1.56% |
| Go 等待 + 150μs 自旋 | 1.0228ms | 1.8175ms | 2.3514ms | 31.77% |
| Go 完整忙等 | 1.0002ms | 1.5155ms | 2.2362ms | 100.00% |

纯等待和 C++ 各项测量 5 秒；150μs 自旋各项 3 秒；完整忙等 5 秒。测量不同时进行，后台负载没有控制，不能对微小差异作因果推断。CPU 统计有量化误差，不能拿此表预测所有电脑或游戏负载。

旧 C++ 引擎空闲时测得约 99.68% 的单核 CPU 占用，与源码持续 `SwitchToThread()` 扫描的行为一致。Go 空闲项是阻塞等待取消，没有活动调度器，测得 CPU 时间为 0；它只是未来无活动宏时的阻塞设计基线。

结论：此 Go 原型平均间隔接近目标，低 CPU 的等待模式有明显资源优势，但 **1ms 的长尾抖动尚未达到旧 C++ 的表现**。增加自旋没有在这几次实验中改善 P99，不能简单用忙等换取稳定性。

后续已按用户选择，正式执行层采用 Go 纯高分辨率等待。C++ 仅保留为历史实现和对照基准，不再是新版运行依赖；这里记录的是最初周期调度实验，不能当作新版完整多宏引擎的端到端性能数据。

尚未测量 `SendInput` 本身、系统输入投递、游戏实际接收、多宏并发、UI 压力和游戏负载，也没有解释 Go 忙等中长尾的具体来源。后续需要重复实验，并分析 Windows 调度、计时周期、Go 运行时和 GC 的影响。

原始数据：

- `baseline-windows.json`：空闲与 1/2/5/10ms，C++/Go 对照。
- `spin150-windows.json`：Go 等待 + 150μs 自旋。
- `busy-windows.json`：Go 1ms 完整忙等。
